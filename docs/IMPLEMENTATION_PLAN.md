# IOCL Prep Hub — Proposed Implementation Plan

Status: awaiting user approval. Do not implement application code until this plan is approved.

## Delivery principle

Build the smallest offline-first tool that accurately runs topic practice and the notified IOCL mock. Content approval gates functionality: an empty state is preferable to an unverified question.

## Phase 0 — Planning and content readiness

Deliverables in this phase:

- approved `docs/SPEC.md`;
- approved `docs/SOURCE_REGISTRY.md`;
- approved `docs/CONTENT_POLICY.md`;
- replacement copies for the two malformed historical GATE PDFs only if those papers are later needed;
- registered explanatory references for any questions selected for the bank.

Exit criteria:

- product scope and exam facts are approved;
- every planned seed question has an allowed provenance, answer evidence, explanation evidence, and reviewer status;
- no local source integrity issue affects the initial question set.

Historical GATE papers are not required to begin the application shell. The malformed 2011 and CS1-2017 files therefore do not block implementation unless their questions are deliberately selected later.

## Phase 1 — Minimal application shell

- Create a Vite React TypeScript app.
- Add only essential scripts: development, build/type-check, lint if generated by the selected Vite template, and tests.
- Use semantic HTML and plain CSS; no component library, router, state library, charting library, or date library initially.
- Add a simple navigation shell for Today, Practice, Mock, Review, Progress, and Sources.
- Display the tentative exam date and official-source disclaimer.

Check: production build passes and all views are keyboard reachable.

## Phase 2 — Trusted content and local model

- Define the minimum `Question`, `Source`, `Attempt`, `Session`, and `Settings` TypeScript types.
- Store approved questions as static TypeScript or JSON data checked into the repository.
- Add a build/test validation that rejects a question missing its answer, explanation, topic, provenance, locator, verification source, or approved status.
- Use one versioned `localStorage` document for user state and one small storage module.
- Handle missing, corrupt, and older stored data without losing the last valid value.

Check: one content-validation test and one storage round-trip/malformed-data test.

## Phase 3 — Topic practice first

- Implement section/topic filters, question count, and timed/untimed mode.
- Render one single-answer MCQ at a time.
- Require a confidence choice before submission.
- Record selected option, correctness, confidence, elapsed time, and review flag.
- Show explanation and source after submission.
- Persist and resume the current session.
- Provide results using answered accuracy and IOCL net score as separate values.

Check: scoring test covers correct, incorrect, unanswered, and low-confidence correct attempts.

This phase is the first useful release and should be used before adding more surface area.

## Phase 4 — Review and weak-area loop

- List incorrect, unanswered, and `guess`/`unsure` correct attempts.
- Filter by section, subject, topic, outcome, and confidence.
- Retry selected questions in a new session while retaining original attempt history.
- Put Computer Networks, Theory of Computation, and timed Quantitative Aptitude at the top until measured results justify a different order.
- Use a deterministic queue: misconceptions first, then fragile correct answers, then other mistakes. No adaptive-learning engine.

Check: a guessed correct answer appears in Review and a retry does not mutate the earlier attempt.

## Phase 5 — Exact IOCL mock mode

- Assemble only approved single-answer MCQs in the 20 Quant / 15 Reasoning / 15 English / 50 Domain distribution.
- Refuse to start when a component lacks enough approved questions.
- Enforce Section A then Section B with 60- and 90-minute timers.
- Support answer navigation, review flags, auto-submit at section timeout, and session recovery after refresh.
- Report raw section marks, overall net mark, unanswered counts, and the applicable official qualifying thresholds.
- State that qualification does not predict shortlisting.

Check: an automated test asserts distribution, fixed order, timers, and `-0.25` scoring.

## Phase 6 — Progress and data safety

- Show compact tables/bars for section and topic attempts, accuracy, net score, time, and confidence calibration.
- Keep CIL baseline values visually separate from IOCL practice history.
- Add validated JSON export/import and confirmed reset.
- Avoid inferred trends until enough attempts exist; show “not enough data” instead.

Check: export/import round trip retains attempts; invalid import leaves current data unchanged.

## Phase 7 — Content QA and release pass

- Run the question validator across the full bank.
- Manually spot-check every explanation and locator selected for the initial release.
- Verify all GATE-derived items show “Official GATE”, not “IOCL previous-year”.
- Verify no CIL question content or personal identifiers are shipped.
- Test keyboard navigation, focus visibility, form labels, contrast, reduced motion, narrow layout, timer announcements, and refresh recovery.
- Recheck the IOCL careers page for corrigenda before release and update verified facts if needed.

Exit criteria:

- build and focused tests pass;
- every visible question is approved and traceable;
- exact mock rules match the latest official notice;
- no prohibited feature or content is present.

## Proposed file shape

Keep the implementation flat until it becomes painful:

```text
src/
  App.tsx
  styles.css
  content/
    questions.ts
    sources.ts
  lib/
    scoring.ts
    storage.ts
  views/
    Today.tsx
    Practice.tsx
    Mock.tsx
    Review.tsx
    Progress.tsx
    Sources.tsx
```

Split files further only when actual size or reuse requires it.

## Deferred until demonstrated necessary

- routing library;
- state-management library;
- charting library;
- spaced-repetition algorithm;
- service worker/PWA packaging;
- bulk content authoring UI;
- difficulty prediction;
- calendar scheduling.

Add one only when the basic practice loop works and a concrete limitation is observed.
